    <h2>What generating it took</h2>
    <p>The schema files are generated. A pipeline reads the specification's markdown and, through a mapping of every field, key, row and statement to a type, generates the JSON Schema 2020-12 files and the rules JSON Schema can't express, each with its test vectors. The mapping and the <Stat of="decisions" /> decisions are recorded by hand, each with the lines of the text it rests on. <a href="how-it-is-built.html">How it's built</a> explains each step. Generating a schema means settling every point a schema needs, and the text doesn't settle all of them.</p>
    <div class="stats">
      <div class="stat gap"><span class="num"><Stat of="gaps" /></span><span class="what">open points filled</span><span class="why">Where the text leaves a point open, a decision fills it. We call these gaps: which value domain a bare <code>String</code> row is of, where a money value reads its currency, what a summary holds.</span></div>
      <div class="stat prop"><span class="num"><Stat of="departures" /></span><span class="what"><Stat of="departures" unit="change we propose" units="changes we propose" /></span><span class="why">Where the text or its examples settle a point and we would write it differently.     <h2>What the schemas cover</h2>
    <p><TypeLink of="Proposal" /> and <TypeLink of="LineItem" /> are the two documents § 4 and § 5 state, and <TypeLink of="ProposalManifest" /> is the third: the whole value of a file a seller publishes at a well-known URL (<Decision of="D-136" />). <TypeLink of="ProposalSummary" />, <TypeLink of="LineItemSummary" /> and <TypeLink of="BuyerWrites" /> are profiles, the paths a block lists read at the types the full form gives them, with the keys the summary's own table adds (<Decision of="D-069" />, <Decision of="D-128" />). Every other structure the text defines is a closed object of its own, <Stat of="objects" count /> of them, and a key an object doesn't list is invalid unless the specification leaves that object to its publisher (<Decision of="D-106" />).</p>
    <p>A line item is of one media channel, <Stat of="channels" count unit="term" /> that § 5.1 writes as a list of its own and the discriminator for how the rest of the line item is read. The text's own code lists are <Stat of="own" unit="vocabulary" units="vocabularies" />; the other <Stat of="registry" count /> are lists another specification on this site publishes, reused under the name it gives them and taken at the commit the registry pins — AdCOM's code lists (<Decision of="D-071" />), its placement's <code>ssai</code> (<Decision of="D-133" />) and the Deals API's price types (<Decision of="D-111" />).</p>
    <p><Stat of="rules" unit="rule" /> state what a schema of one payload can't: one field read against another, an entry that must name an option in another list, which party may change a field between two versions. Each carries at least one valid and one invalid vector, and a vector's valid half is the specification's own bytes (<Decision of="D-134" />).</p>
    <h2>What they leave out</h2>
    <p>§ 2.8's signing profile, this specification's profile of Web Bot Auth, states its rules as prose does and defines no key, type or list, so no schema holds it (<Decision of="D-158" />, <Decision of="D-161" />). § 3's mutability markers say who may change a row, which is a fact about the row and not a value a payload carries, so no file holds the name the rules group them under (<Decision of="D-156" />), and an implementation adds none of its own (<Decision of="D-066" />). Duties no payload can show, such as what a seller must do before it answers, are <Stat of="obligations" unit="obligation" /> of the party they name rather than schema keywords (<Decision of="D-124" />).</p>

    <h2>What a decision record is</h2>
    <p>A decision record is a judgment we recorded wherever the specification leaves a point open, or where we propose a change. Each record has:</p>
    <ul class="ticks">
      <li>the question it answers, and the options we weighed;</li>
      <li>the answer we chose, and why;</li>
      <li>the specification lines it rests on, quoted and pinned, so the record goes stale when those lines change;</li>
      <li>what we ask the specification to state, so that the next revision needs no such record.</li>
    </ul>
    <p>The type map links every type to the records that shape it, and every record to the lines it quotes.</p>
