    <h2>What generating it took</h2>
    <p>A pipeline reads the specification's markdown and, through a mapping of every attribute row, code list and statement to a type, generates the JSON Schema 2020-12 files and the rules JSON Schema can't express, each with test vectors. The mapping and the <Stat of="decisions" /> decisions are recorded by hand, each with the lines of the text it rests on. <a href="how-it-is-built.html">How it's built</a> explains each step.</p>

    <h2>What the schemas cover</h2>
    <p>Two documents: <TypeLink of="Deal" />, the push body, and <TypeLink of="BuyerSeat" />, the status response. Each other object an attribute holds is a closed object of its own, and every object's <code>ext</code> is <TypeLink of="Ext" />, open to the parties' extensions (<Decision of="D-021" />). The text's own code lists are <Stat of="own" unit="vocabulary" />, each code with the label the text gives it, and <TypeLink of="DeviceType" /> and <TypeLink of="CategoryTaxonomy" /> take AdCOM <Stat of="brand.edition" />'s lists from <a href="../adcom/registry.html">the registry on this site</a>, at the commit it pins (<Decision of="D-027" />).</p>
    <h2>What they leave out</h2>
    <p>The text defines no paths, no request body for the status call, no response codes and no authorization, so there is no OpenAPI here: the schemas cover the two payloads (<Decision of="D-025" />). Duties that no payload shows, such as a buyer validating bid requests against the deal, are <Stat of="obligations" unit="obligation" /> of the party they name, not schema keywords.</p>
  </div>

    <h2>How to read the two switches</h2>
    <div class="switch-card">
      <h3>Input</h3>
      <p><strong>main</strong> is the text on the Deals API's <code>main</code> branch, with the errata applied after the tag. <strong>Tag 1.0-202602</strong> is the text at the tag, where <code>sellerstatus</code> gives the code 4 twice (<Decision of="D-010" />).</p>
    </div>
    <div class="switch-card">
      <h3>Variant</h3>
      <p><strong>As written</strong> switches our proposal off, so the field it changes takes the form the text writes. <strong>With our proposals</strong> switches it on. In both, the <Stat of="gaps" /> open points stay filled by their decisions.</p>
    </div>
    <h2>The change we propose</h2>
    <p><Decision of="D-004" /> reads <code>countries</code> as ISO 3166-1 alpha-3, not the ISO-3166-3 the row names: ISO 3166-3 holds the codes of countries that no longer exist, so a deal "available" in them can run nowhere. Its own page states the value the schema takes and the value it refuses.</p>
    <h2>Inputs</h2>
    <Inputs />
    <p>The two inputs differ in one code list, <code>sellerstatus</code>, and in a spelling. The lock comparison classes each schema change as breaking, additive or an annotation.</p>
